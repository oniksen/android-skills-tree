# Асинхронность в Android

**Уровень:** Junior  
**Категория:** Асинхронность  
**Язык:** Kotlin  
**Кратко:** Почему интерфейс нельзя блокировать и как Android-приложение выполняет работу в фоне — от потоков и Looper до корутин.

## 1. Thread и Concurrency Basics {#thread-i-concurrency}

Пользовательский интерфейс Android работает в одном специальном потоке — Main Thread (UI Thread). Если этот поток занят долгой операцией: сетевым запросом, чтением базы данных, сложными вычислениями — интерфейс перестаёт отвечать на касания, а через пять секунд система показывает диалог «Приложение не отвечает» (ANR). Поэтому любую работу, которая длится дольше нескольких миллисекунд, нужно выносить из главного потока в фоновый. Базовым примитивом для этого в JVM служит `Thread` — поток исполнения. Понимание потоков, конкуренции и параллелизма — фундамент, на котором строятся Handler, Looper и корутины.

Поток — это независимая последовательность инструкций, выполняющаяся внутри процесса. Все потоки одного процесса разделяют общую память (кучу), но у каждого есть свой стек вызовов и набор локальных переменных. В Android процесс приложения содержит минимум один поток — главный, а при необходимости создаются дополнительные. Планировщик операционной системы решает, какой поток выполняется в каждый момент времени; на многоядерном процессоре несколько потоков могут работать одновременно.

:::cards
- **Главный поток** — единственный поток, в котором можно менять UI.
- **Фоновый поток** — выполняет тяжёлую работу, не блокируя интерфейс.
- **Общая память** — все потоки видят одни и те же объекты в куче.
- **ANR** — результат блокировки главного потока дольше 5 секунд.
:::

> **Ключевая идея:** Главный поток — это «лицо» приложения. Любая долгая работа на нём превращается в зависание интерфейса. Фоновый поток — способ дать приложению «думать», не мешая пользователю.

### Понятие Thread {#thread-concept}

Класс `java.lang.Thread` представляет поток исполнения в JVM. Каждый объект `Thread` связан с реальным потоком операционной системы (на Android — с pthread). Поток имеет имя, приоритет, состояние и может быть помечен как демон (daemon): демон-потоки не мешают JVM завершить работу, если остались только они.

Состояния потока описаны перечислением `Thread.State`: `NEW` (создан, но не запущен), `RUNNABLE` (готов к выполнению или выполняется), `BLOCKED` (ожидает монитор), `WAITING` (бесконечное ожидание), `TIMED_WAITING` (ожидание с таймаутом), `TERMINATED` (завершён). Эти состояния видны в отладчике, а `Thread.dumpStack()` выводит стек текущего потока — полезно при поиске зависаний.

В Android напрямую создавать `Thread` для каждой задачи не рекомендуется: это дорого по памяти (стек по умолчанию ~1 МБ на поток) и неудобно управлять жизненным циклом. Но понимать, как работает `Thread`, необходимо, потому что все высокоуровневые механизмы (Executor, Handler, корутины) в конечном счёте опираются на потоки.

### Создание потока и Runnable {#thread-create-runnable}

Есть два способа создать поток. Первый — наследоваться от `Thread` и переопределить `run()`. Второй, более гибкий — реализовать интерфейс `Runnable` и передать его в конструктор `Thread`. Второй подход предпочтительнее: он разделяет «что делать» (задача) и «как запускать» (поток), позволяя переиспользовать одну задачу в разных потоках или исполнителях.

```kotlin
// Наследование от Thread
class WorkerThread : Thread() {
    override fun run() {
        println("Работаю в потоке ${currentThread().name}")
    }
}

// Runnable — предпочтительный способ
val task = Runnable {
    println("Задача в потоке ${Thread.currentThread().name}")
}
val thread = Thread(task, "MyWorker")
```

Интерфейс `Runnable` содержит один метод `run()` без возвращаемого значения и без checked-исключений. Если задаче нужно вернуть результат, используют `Callable<V>` и `Future<V>` через `ExecutorService`. В Kotlin лямбда автоматически преобразуется в `Runnable`, поэтому запись `Thread { ... }` работает напрямую.

```kotlin
val thread = Thread {
    val data = loadFromNetwork()
    println("Загружено ${data.size} байт")
}
```

### Запуск и завершение потока {#thread-start-finish}

Поток запускается вызовом `start()`, а не `run()`. Вызов `run()` просто выполнит метод в текущем потоке, как обычную функцию, и не создаст новый поток. После `start()` JVM планирует поток, и его `run()` начнёт выполняться асинхронно. Повторный вызов `start()` на уже запущенном потоке бросает `IllegalThreadStateException`.

Завершение потока происходит естественным путём: когда `run()` возвращает управление, поток переходит в состояние `TERMINATED`. Принудительно остановить поток методом `stop()` нельзя — он устарел и опасен, потому что может оставить объекты в неконсистентном состоянии. Современный подход — кооперативная отмена: поток сам периодически проверяет флаг прерывания через `Thread.currentThread().isInterrupted` или `Thread.interrupted()` и завершается сам.

```kotlin
val thread = Thread {
    while (!Thread.currentThread().isInterrupted) {
        doWork()
    }
    println("Поток завершён корректно")
}
thread.start()
// ... позже
thread.interrupt()
```

Метод `interrupt()` не убивает поток, а лишь устанавливает флаг прерывания (и выводит из `wait`/`sleep`/`join` с `InterruptedException`). Именно поэтому долгие операции должны регулярно проверять этот флаг.

### join() и isAlive {#thread-join-isalive}

`isAlive()` возвращает `true`, если поток был запущен и ещё не завершился. Это простой способ проверить состояние, но его результат устаревает сразу после вызова — не полагайтесь на него для синхронизации.

`join()` заставляет вызывающий поток ждать завершения целевого потока. Перегрузки с таймаутом (`join(millis)`) позволяют не ждать вечно. `join()` бросает `InterruptedException`, если ожидающий поток был прерван.

```kotlin
val worker = Thread {
    Thread.sleep(1000)
    println("Готово")
}
worker.start()
worker.join() // главный поток ждёт 1 секунду
println("Поток завершился: ${!worker.isAlive}")
```

`join()` — базовый инструмент композиции потоков: запустили несколько фоновых задач и дождались их всех перед тем, как продолжить. В корутинах аналогом служит `job.join()`.

### Concurrency vs Parallelism {#thread-concurrency-parallelism}

Конкурентность (concurrency) и параллелизм (parallelism) — разные понятия, хотя их часто путают. Конкурентность — это способность программы управлять несколькими задачами, переключаясь между ними; задачи могут выполняться по очереди на одном ядре. Параллелизм — одновременное выполнение нескольких задач на разных ядрах процессора.

:::cards
- **Concurrency** — несколько задач делаются «вперемешку», даже на одном ядре.
- **Parallelism** — несколько задач выполняются буквально одновременно.
- **Concurrency без parallelism** — один поток на одно ядро переключается между задачами.
- **Требование параллелизма** — несколько ядер и потоков.
:::

Пример: скачивание файла и отрисовка анимации — конкурентная задача. Если обе выполняются одновременно на двух ядрах — это ещё и параллельно. В Android корутины дают конкурентность (многие задачи на ограниченном числе потоков), а `Dispatchers.Default` — параллелизм на пуле потоков.

Различие важно для выбора инструмента: если задачи I/O-bound (сеть, диск), достаточно конкурентности и небольшого пула потоков; если CPU-bound (обработка изображений, вычисления), нужен параллелизм на нескольких ядрах.

### Проблемы доступа к общим данным {#thread-shared-data}

Общая память потоков — источник главных багов многопоточности. Два потока, одновременно меняющие один объект, могут получить состояние, которое невозможно при последовательном выполнении. Классические проблемы:

- **Race condition** — результат зависит от порядка выполнения потоков.
- **Data race** — чтение и запись одного поля без синхронизации; в Java/Kotlin чтение может увидеть частично записанное значение (для `long`/`double` без `@Volatile`).
- **Deadlock** — два потока ждут друг друга, каждый держит ресурс, нужный другому.
- **Livelock** — потоки активно работают, но не продвигаются.
- **Starvation** — поток никогда не получает ресурс из-за других.

Пример гонки:

```kotlin
var counter = 0
repeat(1000) {
    Thread {
        counter++ // не атомарно: прочитать, увеличить, записать
    }.start()
}
// counter почти наверняка меньше 1000
```

Способы защиты: `synchronized { }`-блоки, `@Volatile` для видимости изменений, атомарные классы `AtomicInteger`, `ConcurrentHashMap`, неизменяемые данные, акторы. В корутинах используют `Mutex` и однопоточные контексты. Лучший способ избежать проблем — не разделять изменяемое состояние: передавать данные через сообщения и каналы.

### Blocking vs Non-blocking operations {#thread-blocking-nonblocking}

Блокирующая операция заставляет поток ждать завершения: `Thread.sleep`, чтение из сокета, `Future.get()`. Пока поток заблокирован, он не выполняет ничего полезного, но занимает ресурсы (стек, слот в пуле). Неблокирующая операция возвращает управление сразу, а результат приходит позже через коллбэк, Future или suspend-функцию.

```kotlin
// Блокировка: поток спит 2 секунды
Thread.sleep(2000)

// Неблокировка: запрос уходит, поток свободен
httpClient.newCall(request).enqueue(object : Callback {
    override fun onResponse(call: Call, response: Response) {
        // результат пришёл позже
    }
    override fun onFailure(call: Call, e: IOException) {}
})
```

В Android главный поток никогда не должен выполнять блокирующие операции. Даже короткий `Thread.sleep(100)` на главном потоке вызывает подёргивание анимации. Правило: если операция может ждать (сеть, диск, блокировка), она должна быть либо в фоновом потоке, либо неблокирующей с коллбэком.

Блокирующие вызовы в корутинах (`runBlocking`, `Thread.sleep` внутри корутины) тоже опасны: они блокируют поток диспетчера и могут «заморозить» другие корутины, работающие на том же пуле.

### Типичные ошибки {#thread-errors}

- Вызывать `run()` вместо `start()` и удивляться, что новый поток не появился.
- Повторно вызывать `start()` на завершённом потоке.
- Использовать устаревшие `stop()`/`suspend()`/`resume()`.
- Менять View из фонового потока — крах или непредсказуемое поведение.
- Считать `isAlive()` надёжным условием синхронизации.
- Делить изменяемое состояние между потоками без синхронизации.
- Блокировать главный поток даже на короткое время.

## 2. Handler {#handler}

`Handler` — механизм отправки и обработки сообщений и задач (`Runnable`) в потоке, у которого есть `Looper`. Он нужен для того, чтобы фоновый поток мог безопасно передать результат работы в главный поток и обновить UI, либо запланировать действие на будущее. Handler появился ещё до корутин и остаётся фундаментом Android: на его основе построены `View.post`, `Choreographer`, `Messenger`, `AsyncTask` (устарел) и многие системные механизмы. Понимание Handler необходимо для чтения старого кода и для отладки проблем с потоками.

Handler привязывается к `Looper` конкретного потока в момент создания. Все сообщения, отправленные через этот Handler, попадают в очередь того потока и обрабатываются им. Если Handler создан конструктором без аргументов (устарел с API 30), он привязывается к Looper текущего потока — что часто приводило к крахам, если текущий поток не имел Looper.

:::cards
- **Сообщение** — объект `Message` с данными и кодом what.
- **Runnable** — задача, которую Handler выполнит в своём потоке.
- **Очередь** — `MessageQueue` потока-хоста.
- **Looper** — цикл, который разбирает очередь.
:::

> **Ключевая идея:** Handler — это «почтовый ящик» потока. Любой поток может положить письмо в чужой ящик, а владелец ящика разберёт его, когда освободится. Главный поток имеет такой ящик по умолчанию.

### Handler и его назначение {#handler-purpose}

Назначение Handler — две задачи. Первая: планирование кода на выполнение в потоке, владеющем Looper'ом. Вторая: обмен сообщениями между потоками без явной синхронизации. Handler инкапсулирует и очередь, и диспетчеризацию: вызывающий код не знает, когда именно выполнится задача — только то, что она выполнится в правильном потоке.

Создание Handler для главного потока:

```kotlin
val mainHandler = Handler(Looper.getMainLooper())
```

В старом коде встречается `Handler()` без аргументов — он использует Looper текущего потока. На главном потоке это работает, но в фоновом потоке без Looper бросит исключение. Всегда явно указывайте Looper, чтобы код был предсказуемым.

Handler может обрабатывать сообщения через переопределение `handleMessage(msg: Message)`. Это полезно, когда нужно передавать структурированные данные с кодом `what` и payload в `obj`/`data`. Для простых задач чаще используют `post(Runnable)`.

### Handler.post() {#handler-post}

`post(runnable)` ставит задачу в очередь Looper'а и возвращает `true`, если сообщение успешно поставлено. Задача выполнится, когда Looper дойдёт до неё — обычно в течение нескольких миллисекунд, но не мгновенно и не в момент вызова.

```kotlin
val handler = Handler(Looper.getMainLooper())

thread {
    val result = doHeavyWork()
    handler.post {
        textView.text = result // безопасно: выполняется в Main Thread
    }
}
```

`post` не блокирует вызывающий поток. Если нужно выполнить задачу немедленно и дождаться результата, используйте `runOnUiThread` или корутины с `withContext(Dispatchers.Main)`. Важно: `post` не гарантирует порядок выполнения относительно других источников сообщений, только FIFO внутри одной очереди.

### Handler.postDelayed() {#handler-post-delayed}

`postDelayed(runnable, delayMillis)` планирует задачу на выполнение через указанную задержку. Это базовый механизм таймеров, анимаций и отложенных действий в Android. Задержка отсчитывается от момента вызова, но реальное выполнение может сдвинуться, если главный поток занят.

```kotlin
val handler = Handler(Looper.getMainLooper())

handler.postDelayed({
    showSnackbar("Сессия истекла")
}, 30_000L) // через 30 секунд
```

Типичные применения: автоскрытие подсказки, повторная попытка после ошибки, debounce ввода, периодический опрос. Для повторяющихся задач используют `postDelayed` внутри самого Runnable, создавая цикл. Но для регулярной фоновой работы лучше `WorkManager`, а для анимаций — `Choreographer`/`ViewPropertyAnimator`.

### removeCallbacks() {#handler-remove-callbacks}

`removeCallbacks(runnable)` удаляет из очереди запланированную задачу, если она ещё не выполнена. Это критически важно для предотвращения утечек памяти и выполнения кода для уничтоженных экранов. Если Activity закрылась, а отложенная задача всё ещё в очереди — она выполнится и обратится к уничтоженному View.

```kotlin
class MyActivity : AppCompatActivity() {
    private val handler = Handler(Looper.getMainLooper())
    private val tick = Runnable { updateTimer() }

    override fun onResume() {
        super.onResume()
        handler.postDelayed(tick, 1000)
    }

    override fun onPause() {
        super.onPause()
        handler.removeCallbacks(tick) // обязательно
    }
}
```

Есть перегрузка `removeCallbacks(runnable, token)` для удаления по токену, и `removeMessages(what)` для сообщений. Правило: каждому `postDelayed` должен соответствовать `removeCallbacks` в подходящем коллбэке жизненного цикла. Забыть это — одна из частых причин утечек в старом коде.

### Связь Handler с Looper {#handler-looper-link}

Handler не работает сам по себе: он всегда привязан к `Looper` одного потока. При создании Handler получает Looper (явно или неявно) и использует его `MessageQueue`. Все `post`/`sendMessage` кладут элементы в эту очередь, а Looper разбирает их и вызывает `dispatchMessage` Handler'а.

Один Looper может обслуживать несколько Handler'ов — все они пишут в одну очередь, и Looper вызывает нужный Handler на основе поля `target` сообщения. Наоборот, один Handler привязан ровно к одному Looper на всё время жизни. Сменить Looper нельзя — создайте новый Handler.

```kotlin
// Handler для фонового потока с его Looper
val thread = HandlerThread("worker")
thread.start()
val workerHandler = Handler(thread.looper)

workerHandler.post {
    // выполняется в потоке "worker"
}
```

`HandlerThread` — удобная обёртка: поток с Looper, готовый к использованию. После завершения работы вызовите `thread.quitSafely()`.

### Передача выполнения в Main Thread {#handler-main-thread}

Частая задача: фоновая работа завершилась, нужно обновить UI. Handler с `Looper.getMainLooper()` — классический способ. Альтернативы: `view.post { }`, `Activity.runOnUiThread { }`, `LiveData.postValue`, корутины с `withContext(Dispatchers.Main)`.

```kotlin
val mainHandler = Handler(Looper.getMainLooper())

fun fetchUser(id: Long, onResult: (User) -> Unit) {
    thread {
        val user = api.getUser(id) // фоновый поток
        mainHandler.post {
            onResult(user) // главный поток
        }
    }
}
```

Важно: не передавайте тяжёлые объекты через замыкание, если они могут измениться. Захватывайте финальное значение. И не забывайте отменять отложенные задачи при уничтожении экрана.

В современном Kotlin-коде Handler для перехода на Main Thread чаще заменяют корутинами: `withContext(Dispatchers.Main) { ... }` читается линейно и управляется структурированной конкуренцией. Но Handler всё ещё нужен для низкоуровневых сценариев и интеграции с Java-библиотеками.

### Типичные сценарии использования {#handler-typical-scenarios}

Handler применяют в следующих случаях:

- Обновление UI после фоновой работы, если не используются корутины/LiveData.
- Отложенные действия: таймаут, автоскрытие, повтор.
- Периодические задачи через цикл `postDelayed`.
- Обмен сообщениями между процессами через `Messenger` (Handler на стороне сервиса).
- Интеграция с API, принимающими `Handler` (например, `SensorManager`).
- Управление очередью задач в собственном потоке с Looper.

Для новых проектов большинство этих задач решают корутины, Flow и WorkManager. Handler остаётся важным для понимания того, как работает Android под капотом, и для поддержки легаси-кода.

### Типичные ошибки {#handler-errors}

- Создавать `Handler()` в фоновом потоке без Looper — крах с `RuntimeException`.
- Забывать `removeCallbacks` при уничтожении Activity/Fragment — утечка и краш.
- Обращаться к View из `handleMessage`, если Handler привязан не к главному потоку.
- Предполагать, что `post` выполняется мгновенно — он ставится в очередь.
- Создавать множество Handler'ов вместо одного на Looper.
- Использовать Handler для CPU-тяжёлых задач — он не создаёт потоков, только диспетчеризует.
- Захватывать `this` Activity в Runnable и не отменять — утечка.

## 3. Looper и MessageQueue {#looper-i-messagequeue}

`Looper` — это цикл обработки сообщений потока: бесконечный цикл, который читает сообщения из очереди и передаёт их Handler'ам. `MessageQueue` — сама очередь. Вместе они образуют event loop Android: главный поток — это Looper, который бесконечно разбирает очередь событий (касания, отрисовка, таймеры, сообщения от Handler). Понимание этой пары объясняет, почему UI не может «сам по себе» выполнять код параллельно и почему `post` не мгновенный.

Каждый поток может иметь не более одного Looper. Looper создаётся через `Looper.prepare()`, который создаёт `MessageQueue` и привязывает Looper к текущему потоку. Затем вызывается `Looper.loop()` — бесконечный цикл. Поток, в котором вызван `loop()`, блокируется навсегда (до `quit()`), поэтому Looper-поток — это отдельный поток, посвящённый обработке сообщений.

:::cards
- **Looper** — цикл `loop()`, читающий сообщения из очереди.
- **MessageQueue** — связный список сообщений, отсортированный по времени.
- **Main Looper** — Looper главного потока, создаётся системой.
- **ThreadLocal** — Looper хранится в потоке через ThreadLocal.
:::

> **Ключевая идея:** Главный поток Android — это просто поток с Looper'ом, который бесконечно разбирает очередь. Ваш код, запущенный на главном потоке, — это одно из сообщений в этой очереди.

### Назначение Looper {#looper-purpose}

Назначение Looper — дать потоку способность получать и обрабатывать асинхронные сообщения. Без Looper поток выполняет свою функцию `run()` и завершается. С Looper поток живёт до явного вызова `quit()` и может принимать задачи извне. Это превращает поток из «одноразового исполнителя» в «сервер сообщений».

Looper используется внутри Android повсеместно: главный поток, `HandlerThread`, `IntentService` (устарел), `Messenger`, `Choreographer` (синхронизация с VSYNC), рендеринг. В обычной разработке приложений вы редко создаёте Looper вручную — система и библиотеки делают это за вас. Но понимание Looper необходимо для отладки «зависаний» главного потока: если в очереди скопилось много тяжёлых сообщений, каждое следующее ждёт.

### MessageQueue {#message-queue}

`MessageQueue` — очередь сообщений потока. Внутри это не обычная FIFO-очередь, а связный список `Message`, отсортированный по полю `when` (время выполнения в миллисекундах системного времени). Сообщения с одинаковым временем выполняются в порядке поступления. `MessageQueue` управляется Looper'ом и Handler'ами; напрямую с ней работают редко.

Когда вы вызываете `postDelayed(runnable, 1000)`, Handler создаёт `Message` с `when = now + 1000` и вставляет в очередь в нужное место. Looper в `loop()` вызывает `queue.next()`, который блокируется, если ближайшее сообщение ещё не готово (через native-ожидание на файловом дескрипторе). Как только время приходит, `next()` возвращает сообщение, и Looper вызывает `msg.target.dispatchMessage(msg)`.

```kotlin
// Низкоуровневый доступ (обычно не нужен)
val queue = Looper.myQueue()
queue.addIdleHandler {
    // вызывается, когда очередь пуста
    true // вернуть true, чтобы оставаться idle-обработчиком
}
```

`addIdleHandler` полезен для отложенной инициализации: выполнить работу, когда главный поток свободен.

### Main Looper {#main-looper}

Главный поток приложения имеет Looper, создаваемый системой до вызова `Application.onCreate`. Получить его можно через `Looper.getMainLooper()`. Это единственный Looper, который гарантированно существует в любом приложении. Все операции с UI должны выполняться в потоке этого Looper'а.

```kotlin
val isMainThread = Looper.myLooper() == Looper.getMainLooper()

fun ensureMainThread() {
    check(Looper.myLooper() == Looper.getMainLooper()) {
        "Вызов только из главного потока"
    }
}
```

Система использует Main Looper для доставки всех UI-событий: касания, отрисовка кадров, жизненный цикл Activity/Fragment. Если главный поток занят долгой операцией, очередь растёт, события обрабатываются с задержкой — интерфейс «зависает». Отсюда правило: главный поток должен быть свободен всегда, а тяжёлая работа — в фоне.

### Связь Looper, Handler и MessageQueue {#looper-handler-queue}

Три класса образуют единую систему:

- `Looper` — владеет `MessageQueue` и запускает цикл.
- `MessageQueue` — хранит `Message` и `Runnable` (упакованные в `Message`).
- `Handler` — интерфейс для отправки в очередь и обработки сообщений.

Связь: Handler при создании получает Looper (и через него MessageQueue). При `post`/`sendMessage` Handler создаёт `Message`, устанавливает `msg.target = this` (сам Handler) и кладёт в очередь Looper'а. Looper в цикле достаёт сообщение и вызывает `target.dispatchMessage(msg)`, который либо вызывает `handleMessage`, либо `run()` Runnable'а.

```kotlin
val looper = Looper.getMainLooper()
val queue = looper.queue // MessageQueue
val handler = Handler(looper) // привязан к этому Looper и queue
```

Один Looper — одна очередь — много Handler'ов. Все Handler'ы, привязанные к одному Looper, пишут в одну очередь, и Looper разбирает их в порядке времени. Это гарантирует, что задачи на главном потоке выполняются последовательно, без гонок.

### Цикл обработки сообщений {#message-loop}

Метод `Looper.loop()` — бесконечный цикл:

1. Вызвать `queue.next()` — получить следующее сообщение (блокируется, если очередь пуста или ближайшее сообщение не готово).
2. Если сообщение `null` — очередь завершена (`quit()`), выйти из цикла.
3. Вызвать `msg.target.dispatchMessage(msg)`.
4. Переработать сообщение (`msg.recycle()`).
5. Повторить.

Вся работа главного потока — это выполнение шага 3 для очередного сообщения. Когда вы вызываете `textView.text = "..."`, это происходит внутри одного из таких сообщений. Если внутри шага 3 выполняется долгая операция, следующее сообщение (например, касание пользователя) ждёт — интерфейс зависает.

```kotlin
// Псевдокод loop()
fun loop() {
    while (true) {
        val msg = queue.next() ?: break
        msg.target.dispatchMessage(msg)
        msg.recycle()
    }
}
```

Именно поэтому нельзя «запустить фоновую работу» на главном потоке и ожидать, что система сама её распараллелит. Главный поток выполняет одну задачу за раз.

### Почему не требуется вручную создавать Looper для обычной разработки {#looper-manual}

В обычной разработке приложений Looper создаётся системой: главный поток получает его автоматически, а для фоновых задач используют готовые механизмы — `HandlerThread`, `ExecutorService`, корутины с диспетчерами. Ручной `Looper.prepare()` + `Looper.loop()` нужен только в специальных случаях: собственный поток-сервер сообщений, интеграция с `Messenger`, низкоуровневая работа с системными API.

Создание Looper вручную требует аккуратности: нужно вызвать `prepare()` в потоке, затем `loop()`, а при завершении — `quit()`/`quitSafely()`. Забыть `quit()` — утечка потока. Вызвать `prepare()` дважды в одном потоке — `RuntimeException`. Использовать Looper из другого потока без синхронизации — ошибки видимости.

```kotlin
// Так делать обычно не нужно
class MyLooperThread : Thread() {
    lateinit var handler: Handler
    override fun run() {
        Looper.prepare()
        handler = Handler(Looper.myLooper()!!)
        Looper.loop() // блокирует поток навсегда
    }
}
```

Для фоновой работы с сообщениями используйте `HandlerThread` — он инкапсулирует `prepare`/`loop` и корректно завершается через `quitSafely()`.

### Типичные ошибки {#looper-errors}

- Вызывать `Looper.prepare()` в потоке, где Looper уже есть.
- Забывать `quit()`/`quitSafely()` для собственного Looper-потока — утечка.
- Предполагать, что `post` выполняется немедленно — сообщение ждёт своей очереди.
- Блокировать главный поток долгой операцией — очередь растёт, ANR.
- Обращаться к `Looper.myLooper()` в потоке без Looper — вернёт `null`.
- Создавать Looper для задач, которые лучше решают корутины или Executor.
- Путать `quit()` (немедленно) и `quitSafely()` (после обработки текущих сообщений).

## 4. Coroutines Basics {#coroutines-basics}

Kotlin Coroutines — библиотека для асинхронного и неблокирующего программирования. Корутина — это вычисление, которое можно приостановить и возобновить, не блокируя поток. В отличие от потоков, корутины дешёвые: можно запустить тысячи корутин на нескольких потоках. Они пишутся как обычный синхронный код с `suspend`-функциями, но выполняются асинхронно. В Android корутины — основной инструмент для фоновой работы с 2019 года (после объявления Google о поддержке).

Корутины решают три проблемы потоков: дорогостоящее создание, сложное управление жизненным циклом и «ад коллбэков». Код с корутинами читается линейно: `val user = api.getUser(id)` выглядит как синхронный вызов, но под капотом приостанавливается, пока идёт сеть, и возобновляется с результатом. Это делает асинхронный код похожим на синхронный, но без блокировки потоков.

:::cards
- **Дёшево** — тысячи корутин на нескольких потоках.
- **Линейно** — асинхронный код читается как синхронный.
- **Структурированно** — корутины образуют дерево с автоматической отменой.
- **Интеграция** — работает с Flow, Room, Retrofit, ViewModel.
:::

> **Ключевая идея:** Корутина — это не поток, а задача, которая умеет «засыпать» и «просыпаться» на потоке. Потоки — рабочие, корутины — задачи, которые они выполняют.

### Назначение Kotlin Coroutines {#coroutines-purpose}

Назначение корутин — сделать асинхронный код простым, безопасным и управляемым. Они заменяют коллбэки, `AsyncTask`, `RxJava` (частично) и ручное управление потоками. Корутины интегрированы в язык (ключевое слово `suspend`), а официальная библиотека `kotlinx.coroutines` не требует сторонних фреймворков.

Корутины подходят для: сетевых запросов, работы с базой данных, файловыми операциями, таймеров, анимаций, обработки потоков данных (Flow). Они не подходят для CPU-тяжёлых задач без правильного диспетчера — для этого используют `Dispatchers.Default`.

Библиотека `kotlinx.coroutines` предоставляет строительные блоки: `launch`, `async`, `runBlocking`, `coroutineScope`, `supervisorScope`, `flow`, диспетчеры. В Android добавляются `viewModelScope`, `lifecycleScope`, `Dispatchers.Main.immediate`.

### launch {#coroutines-launch}

`launch` запускает новую корутину «выстрелил и забыл» (fire-and-forget): возвращает `Job`, не возвращает результат. Используется, когда нужно выполнить действие без ожидания результата: сохранить данные, отправить аналитику, обновить UI.

```kotlin
viewModelScope.launch {
    val user = repository.getUser(id) // suspend-функция
    _uiState.value = UiState.Success(user)
}
```

`launch` должен вызываться в контексте `CoroutineScope`. Сам по себе `launch` — это функция-расширение `CoroutineScope`, поэтому без scope его не вызвать. Блок кода внутри `launch` — это тело корутины; внутри можно вызывать suspend-функции.

`launch` не блокирует вызывающий код: он планирует корутину и сразу возвращает `Job`. Если нужен результат, используйте `async`.

### async и await {#coroutines-async-await}

`async` запускает корутину, которая вычисляет и возвращает значение типа `Deferred<T>`. Чтобы получить значение, вызывают `await()` — suspend-функцию, которая приостанавливается до завершения вычисления. `async` полезен для параллельного запуска нескольких независимых задач.

```kotlin
suspend fun loadDashboard(): Dashboard = coroutineScope {
    val userDeferred = async { api.getUser() }
    val ordersDeferred = async { api.getOrders() }
    Dashboard(
        user = userDeferred.await(),
        orders = ordersDeferred.await()
    )
}
```

Здесь два запроса выполняются параллельно, а `await()` собирает результаты. Если один из них упадёт с исключением, `await()` пробросит его. `async` без `await` — утечка: корутина выполнится, но результат потеряется, а исключение может быть проглочено (в зависимости от scope).

Разница с `launch`: `launch` для побочных эффектов, `async` для вычисления значения. Не используйте `async` там, где не нужен результат.

### runBlocking и область его применения {#coroutines-runblocking}

`runBlocking` создаёт корутину и блокирует текущий поток до её завершения. Используется как мост между синхронным и асинхронным кодом: в `main()`, в тестах, в инициализации. В Android-приложении `runBlocking` почти никогда не нужен на главном потоке — он заблокирует UI.

```kotlin
fun main() = runBlocking {
    val data = fetchData() // suspend
    println(data)
}
```

В тестах `runBlocking` удобен:

```kotlin
@Test
fun `loadUser returns user`() = runBlocking {
    val user = repository.getUser(1L)
    assertEquals("Ada", user.name)
}
```

Правило: `runBlocking` — только на границе с синхронным миром (main, тесты, скрипты). Внутри приложения используйте scope'ы (`viewModelScope`, `lifecycleScope`) и suspend-функции. Блокировать поток внутри корутины через `runBlocking` — анти-паттерн.

### CoroutineScope {#coroutines-scope}

`CoroutineScope` определяет область жизни корутин: все корутины, запущенные в scope, принадлежат ему и отменяются вместе с ним. Scope содержит `CoroutineContext` (диспетчер, Job, обработчик исключений). В Android готовые scope'ы привязаны к жизненному циклу: `viewModelScope` (очищается при `onCleared`), `lifecycleScope` (отменяется при уничтожении), `rememberCoroutineScope` в Compose.

```kotlin
class MyViewModel : ViewModel() {
    fun load() {
        viewModelScope.launch {
            // отменится автоматически при очистке ViewModel
            val data = repository.load()
            _state.value = data
        }
    }
}
```

Можно создать собственный scope: `CoroutineScope(SupervisorJob() + Dispatchers.Main)`. Но тогда нужно вручную вызывать `scope.cancel()` при уничтожении владельца, иначе — утечка. Поэтому предпочтительны готовые scope'ы.

### Job {#coroutines-job}

`Job` представляет выполняющуюся корутину. Каждый `launch`/`async` возвращает Job (или Deferred, который наследует Job). Job образует дерево: родительский Job содержит дочерние. Состояния Job (основные): `New`, активный (active), завершающийся (completing), отменяющийся (cancelling), завершён (completed), отменён (cancelled). Job можно отменить через `cancel()`, дождаться завершения через `join()`, проверить `isActive`, `isCompleted`, `isCancelled`.

```kotlin
val job = viewModelScope.launch {
    repeat(1000) { i ->
        delay(100)
        println("шаг $i")
    }
}
// позже
job.cancel()
```

Job — единица управления жизненным циклом. Хранение Job позволяет отменить конкретную задачу, не трогая другие корутины scope'а. В структурированной конкуренции Job родителя отменяет всех детей при своей отмене.

### cancel() и join() {#coroutines-cancel-join}

`cancel()` запрашивает отмену корутины. Отмена кооперативная: корутина должна сама проверять отмену (через `isActive`, `ensureActive()`, или при вызове suspend-функций, которые проверяют отмену). `cancel()` не прерывает поток принудительно.

`join()` приостанавливает вызывающую корутину до завершения Job. Комбинация `cancel()` + `join()` — стандартный способ «остановить и дождаться»:

```kotlin
job.cancel()
job.join() // дождаться завершения (с отменой)
// или
job.cancelAndJoin()
```

После отмены корутина выбрасывает `CancellationException` (или завершается нормально, если уже завершилась). `CancellationException` не считается ошибкой и не пробрасывается родителю. Долгие циклы должны вызывать `yield()` или `ensureActive()`, чтобы отмена сработала вовремя:

```kotlin
suspend fun process(items: List<Item>) {
    for (item in items) {
        ensureActive() // бросит CancellationException, если отменено
        processItem(item)
    }
}
```

### Structured Concurrency {#coroutines-structured-concurrency}

Структурированная конкуренция (structured concurrency) — принцип: корутины образуют дерево, и родитель не завершится, пока не завершатся все дети. Отмена родителя отменяет всех детей. Исключение в ребёнке пробрасывается родителю (если не использовать `SupervisorJob`). Это делает утечки и «висящие» корутины невозможными по конструкции.

```kotlin
suspend fun loadAll() = coroutineScope {
    val a = async { fetchA() }
    val b = async { fetchB() }
    a.await() + b.await()
} // scope завершится только когда обе async завершатся
```

Если `fetchA()` бросит исключение, `coroutineScope` отменит `fetchB()` и пробросит исключение наружу. Это предсказуемое поведение, в отличие от коллбэков, где ошибка могла потеряться.

`supervisorScope` — вариант, где сбой одного ребёнка не отменяет остальных. Используется, когда задачи независимы (например, загрузка нескольких виджетов). В обычном коде предпочитайте `coroutineScope`.

### Типичные ошибки {#coroutines-errors}

- Вызывать suspend-функции вне корутины или другой suspend-функции.
- Использовать `GlobalScope` — корутины не привязаны к жизненному циклу, утечки.
- Забывать `await()` у `async` — потеря результата и исключений.
- Блокировать поток внутри корутины (`Thread.sleep`, `runBlocking`) — блокирует диспетчер.
- Не проверять отмену в долгих циклах — корутина не отменится.
- Ловить `CancellationException` и не пробрасывать — ломает отмену.
- Путать `launch` (нет результата) и `async` (есть результат).

## 5. Dispatchers {#dispatchers}

Диспетчер (Dispatcher) определяет, в каком потоке (или пуле потоков) выполняется корутина и её продолжения. Выбор диспетчера — это выбор ресурса: главный поток UI, пул для блокирующего ввода-вывода или пул для вычислений. Правильный выбор влияет на отзывчивость интерфейса и на то, не «съест» ли фоновая задача все потоки приложения.

### 5.1. Dispatchers.Main {#dispatchers-main}

`Dispatchers.Main` привязан к главному (UI) потоку Android. На нём можно трогать View, обновлять Compose-состояние, показывать Toast и диалоги. Тяжёлую работу на нём делать нельзя: любая блокировка заморозит интерфейс и приведёт к ANR.

```kotlin
import kotlinx.coroutines.Dispatchers
import kotlinx.coroutines.withContext

suspend fun updateUi(text: String) {
    withContext(Dispatchers.Main) {
        textView.text = text
    }
}
```

В Android `Dispatchers.Main` предоставляется артефактом `kotlinx-coroutines-android`, который нужно подключить как зависимость. В unit-тестах без Android-окружения его подменяют через `Dispatchers.setMain(...)` из `kotlinx-coroutines-test`, а после теста восстанавливают через `Dispatchers.resetMain()`. Есть вариант `Dispatchers.Main.immediate`: если корутина уже выполняется в главном потоке, продолжение выполняется сразу, без постановки в очередь, что снижает задержки при обновлении UI.

### 5.2. Dispatchers.IO {#dispatchers-io}

`Dispatchers.IO` — пул потоков для блокирующих операций: сетевые запросы, чтение/запись файлов, запросы к SQLite/Room (если не использовать suspend-DAO), работа с SharedPreferences в больших объёмах. Пул эластичный: по умолчанию не меньше 64 потоков — `max(64, число ядер)`, поэтому на многоядерных машинах их больше 64, потоки создаются по требованию и переиспользуются.

```kotlin
suspend fun readConfig(file: File): String = withContext(Dispatchers.IO) {
    file.readText()
}
```

Не запускайте на `IO` CPU-интенсивные циклы: они займут потоки, предназначенные для ожидания I/O, и замедлят реальные операции ввода-вывода. Для вычислений есть `Dispatchers.Default`.

### 5.3. Dispatchers.Default {#dispatchers-default}

`Dispatchers.Default` — пул потоков размером с число ядер CPU (минимум 2). Предназначен для CPU-bound работы: сортировка, фильтрация больших списков, парсинг JSON, криптография, сложные вычисления. Потоки не блокируются ожиданием — они должны быть заняты вычислениями.

```kotlin
suspend fun sortItems(items: List<Item>): List<Item> =
    withContext(Dispatchers.Default) {
        items.sortedBy { it.priority }
    }
```

Если запустить на `Default` блокирующую операцию (например, `Thread.sleep` или синхронный сетевой вызов), один из немногих потоков пула будет простаивать, и параллелизм вычислений упадёт. Для блокировок используйте `IO`.

### 5.4. withContext {#withcontext}

`withContext(dispatcher)` — suspend-функция, которая переключает контекст выполнения текущей корутины на указанный диспетчер, выполняет блок и возвращает результат. Она не создаёт новую корутину и не нарушает structured concurrency: родительская Job остаётся той же, отмена распространяется.

```kotlin
suspend fun loadUser(id: Int): User {
    val dto = withContext(Dispatchers.IO) {
        api.getUser(id) // сетевой вызов
    }
    return withContext(Dispatchers.Default) {
        dto.toDomain() // преобразование
    }
}
```

Результат блока становится результатом `withContext`. Если блок бросает исключение, оно пробрасывается наружу, а диспетчер восстанавливается. `withContext` — основной инструмент тонкой настройки потоков внутри одной корутины.

### 5.5. CPU-bound и I/O-bound задачи {#cpu-bound-i-io-bound}

Классификация задач по типу нагрузки определяет выбор диспетчера.

- I/O-bound: время выполнения определяется ожиданием внешнего ресурса (сеть, диск, БД). Поток большую часть времени простаивает. Примеры: загрузка картинки, запись файла, SQL-запрос. Подходит `Dispatchers.IO`.
- CPU-bound: время выполнения определяется вычислениями на процессоре. Поток загружен на 100%. Примеры: сортировка, сериализация, фильтрация, расчёт хэша. Подходит `Dispatchers.Default`.

Ошибка классификации приводит к двум проблемам. CPU-работа на `IO` создаёт лишние потоки (до 64) и тратит память. I/O-работа на `Default` блокирует один из немногих потоков вычислений, и другие корутины ждут. При сомнении разбивайте задачу: сначала I/O на `IO`, затем обработка на `Default`.

### 5.6. Переключение контекста выполнения {#pereklyuchenie-konteksta}

Переключение контекста — это смена потока, на котором продолжается корутина после suspend-точки. Оно происходит в двух случаях: при явном `withContext` и при вызове suspend-функции, внутри которой есть `withContext` или встроенный переключатель (например, `delay` возобновляет на том же диспетчере, а `flowOn` меняет upstream).

Частые переключения стоят дёшево, но не бесплатны: каждое включает планирование задачи в пул потоков. На горячих путях (например, в цикле по тысячам элементов) переключаться на каждый элемент не нужно — лучше собрать данные в один `withContext` и обработать разом.

Контекст (включая Job и диспетчер) наследуется дочерними корутинами. `launch` и `async` по умолчанию используют диспетчер родителя, если не указан явно. Это позволяет централизованно задать диспетчер для целой области.

### 5.7. Почему suspend-функция сама по себе не переключает поток {#pochemu-suspend-ne-pereklyuchaet}

Ключевое слово `suspend` означает «эту функцию можно приостановить», но не «она выполняется в другом потоке». Suspend-функция по умолчанию работает на диспетчере вызывающего кода. Если её вызвали из корутины на `Dispatchers.Main`, тело функции (до первой suspend-точки) тоже выполняется на главном потоке.

```kotlin
suspend fun fetchUser(id: Int): User {
    // на диспетчере вызывающего кода!
    val response = api.get(id) // suspend+withContext(IO) переключит
    return response.toUser()
}
```

Распространённая ошибка: написать `suspend fun` и считать, что сеть автоматически уйдёт в фон. Если внутри нет `withContext(Dispatchers.IO)` или suspend-вызова с переключением, блокирующий код (например, `execute()` OkHttp) заблокирует главный поток. Правило: suspend-функция, делающая блокирующий вызов, обязана сама переключить диспетчер через `withContext`.

**Типичные ошибки:**
- Выполнение сетевого или файлового I/O на `Dispatchers.Default` или `Dispatchers.Main`.
- Предположение, что `suspend` автоматически уводит код в фоновый поток.
- Создание слишком многих корутин на `Dispatchers.IO` без необходимости.
- Частые `withContext` внутри циклов.
- Использование `Dispatchers.Main` в unit-тестах без замены.

**Короткая самопроверка:**

- [ ] Понимаю разницу `Dispatchers.IO` и `Dispatchers.Default`.
- [ ] Использую `withContext` для переключения потока внутри suspend-функции.
- [ ] Знаю, что `suspend` сам по себе не меняет поток.

## 6. Suspend Functions и Cancellation {#suspend-functions-i-cancellation}

Suspend-функции — центральный механизм корутин: они позволяют писать асинхронный код последовательно, без коллбэков. Отмена корутин кооперативная: код сам должен проверять, не отменена ли задача. Понимание этих двух идей отличает рабочий код от кода, который «зависает» или игнорирует отмену.

### 6.1. Ключевое слово suspend {#klyuchevoe-slovo-suspend}

`suspend` помечает функцию как приостанавливаемую. Такую функцию можно вызвать только из другой suspend-функции или из корутины (внутри `launch`/`async`/`runBlocking`). Компилятор преобразует её в функцию с дополнительным параметром-продолжением (continuation) и генерирует конечный автомат.

```kotlin
suspend fun fetchPosts(): List<Post> {
    delay(1000) // suspend-точка
    return api.getPosts()
}
```

`suspend` не делает функцию асинхронной «магически»: если внутри нет suspend-вызовов, она выполняется синхронно на текущем диспетчере. Аннотация лишь разрешает использовать внутри другие suspend-функции и быть приостановленной.

### 6.2. Вызов suspend-функций {#vyzov-suspend-funkcij}

Suspend-функции вызываются как обычные: `val posts = fetchPosts()`. Выполнение приостанавливается на каждой suspend-точке (вызове другой suspend-функции или `delay`), освобождая поток, и возобновляется, когда результат готов. По умолчанию вызовы последовательны: вторая функция начнётся только после завершения первой.

```kotlin
launch {
    val user = fetchUser(id)   // ждём
    val posts = fetchPosts()    // потом этот
    show(user, posts)
}
```

Для параллельного выполнения используют `async` + `await`. Suspend-функция может вернуть значение, бросить исключение или быть отменена — в последнем случае бросается `CancellationException`.

### 6.3. Suspension vs Blocking {#suspension-vs-blocking}

- Suspension (приостановка): корутина «засыпает», а поток возвращается в пул и может выполнять другие корутины. Ресурсы не простаивают. Пример: `delay(1000)`, ожидание ответа сети через suspend-вызов.
- Blocking (блокировка): поток занят ожиданием и ничего другого делать не может. Пример: `Thread.sleep(1000)`, синхронный `execute()`.

```kotlin
// плохо: блокирует поток на секунду
Thread.sleep(1000)

// хорошо: корутина приостанавливается
delay(1000)
```

Использование блокирующих вызовов внутри корутин на `Dispatchers.Main` или `Dispatchers.Default` приводит к зависаниям и ANR. Если блокирующий API неизбежен (старая библиотека), оборачивайте его в `withContext(Dispatchers.IO)`.

### 6.4. Continuation (общее понимание) {#continuation}

Continuation (продолжение) — объект, представляющий «что делать дальше» после приостановки. На уровне языка suspend-функция компилируется в конечный автомат: локальные переменные и точка возобновления сохраняются в полях класса-continuation. Когда результат готов, вызывается `resumeWith(result)`, и функция продолжает с нужного места.

Разработчику обычно не нужно работать с `Continuation` напрямую. Но понимание помогает читать стектрейсы (в них появляются `ContinuationImpl`, `resumeWith`) и понимать, почему suspend-функция может возобновиться на другом потоке: продолжение планируется диспетчером, связанным с контекстом.

```kotlin
// низкоуровневый пример
suspend fun example() = suspendCoroutine { cont ->
    someAsyncApi { result -> cont.resume(result) }
}
```

`suspendCoroutine`/`suspendCancellableCoroutine` — мост между корутинами и коллбэк-API. В обычном коде предпочитают готовые suspend-обёртки.

### 6.5. Кооперативная отмена корутин {#kooperativnaya-otmena}

Отмена в корутинах кооперативная: вызов `job.cancel()` не прерывает код насильно, а выставляет флаг отмены. Реальная остановка происходит в suspend-точках: `delay`, `yield`, операции с каналами/Flow проверяют флаг и бросают `CancellationException`. Если корутина выполняет долгий CPU-цикл без suspend-точек, она не отменится, пока не дойдёт до такой точки.

```kotlin
val job = scope.launch {
    repeat(1_000_000) { i ->
        // нет suspend-точки
        doWork(i)
    }
}
job.cancel() // флаг установлен
```

Чтобы цикл был отменяемым, добавляйте проверки (см. 6.7). Это ключевое отличие от `Thread.interrupt()`, который пытается прервать поток.

### 6.6. CancellationException {#cancellation-exception}

`CancellationException` — специальное исключение, сигнализирующее об отмене корутины. Оно не должно перехватываться как обычная ошибка: если поймать `Exception` и не пробросить `CancellationException`, отмена сломается, и корутина продолжит работу после отмены.

```kotlin
try {
    doWork()
} catch (e: CancellationException) {
    throw e // обязательно пробросить
} catch (e: Exception) {
    handleError(e)
}
```

Или проверяйте тип: `if (e is CancellationException) throw e`. В `runCatching` и общих обработчиках это особенно важно. `CancellationException` также не считается сбоем родительской корутины: она означает штатное завершение по отмене, а не ошибку.

### 6.7. Проверка отмены в длительных операциях {#proverka-otmeni}

Для долгих вычислений используйте явные проверки:

- `ensureActive()` — бросает `CancellationException`, если корутина отменена. Удобно вставлять в циклы.
- `isActive` — свойство `CoroutineScope`/`Job`; можно проверить и выйти из цикла вручную.
- `yield()` — suspend-точка, которая также проверяет отмену и даёт другим корутинам шанс выполниться.

```kotlin
scope.launch(Dispatchers.Default) {
    for (item in hugeList) {
        ensureActive() // бросит CancellationException при отмене
        process(item)
    }
}
```

Для блокирующих вызовов используйте `suspendCancellableCoroutine` и регистрируйте обработчик отмены через `invokeOnCancellation`, чтобы отменить нижележащую операцию (например, OkHttp `Call.cancel()`).

### 6.8. Базовое распространение ошибок между дочерними корутинами {#rasprostranenie-oshibok}

В structured concurrency ошибка в дочерней корутине отменяет родителя и всех его других детей — это поведение по умолчанию (`Job`). Если одна из параллельных задач падает, остальные отменяются, а исключение пробрасывается в точку ожидания.

```kotlin
scope.launch {
    try {
        coroutineScope {
            launch { taskA() } // если упадёт
            launch { taskB() } // будет отменена
        }
    } catch (e: Exception) {
        // получит исключение из taskA
    }
}
```

Если нужно, чтобы сбой одной задачи не отменял остальные, используют `supervisorScope` и `SupervisorJob`: дети становятся независимыми, а ошибка обрабатывается в каждом `launch` отдельно. Это базовое понятие; тонкая настройка обработки ошибок относится к следующему уровню.

**Типичные ошибки:**
- Перехват `Exception` с игнорированием `CancellationException`.
- Долгие CPU-циклы без `ensureActive`/`yield`.
- Использование `GlobalScope`, ломающее structured concurrency.
- Предположение, что `cancel()` мгновенно останавливает код.
- Необработанные исключения в дочерних корутинах, роняющие всю область.

## 7. Flow Basics {#flow-basics}

Flow — это реактивный поток данных в корутинах: последовательность значений, которые эмитятся со временем. В отличие от обычной функции, возвращающей один результат, Flow может выдать много значений и завершиться (или не завершиться никогда). Это основа реактивного UI на Android: экран подписывается на поток состояния и перерисовывается при каждом новом значении.

### 7.1. Реактивный поток данных {#reaktivnyj-potok}

Реактивный поток — абстракция «значения, приходящие со временем». Потребитель (collector) реагирует на каждое новое значение, а не опрашивает источник. Это устраняет ручную синхронизацию: UI просто собирает Flow и обновляется.

В Android реактивность чаще всего проявляется так: репозиторий отдаёт `Flow<List<Item>>`, ViewModel преобразует его в `StateFlow<UiState>`, а Compose/Fragment собирает и рисует. При изменении данных в БД поток сам доставляет новое значение до экрана.

### 7.2. flow { emit() } {#flow-emit}

Холодный поток создаётся билдером `flow { }`. Внутри вызывают `emit(value)`, чтобы отправить значение потребителю. Код билдера выполняется заново для каждого нового коллектора.

```kotlin
import kotlinx.coroutines.flow.Flow
import kotlinx.coroutines.flow.flow

fun countdown(from: Int): Flow<Int> = flow {
    for (i in from downTo 0) {
        emit(i)
        delay(1000)
    }
}
```

Билдер — suspend-контекст: внутри можно вызывать suspend-функции (`delay`, `withContext`). `emit` — suspend-функция: она приостанавливается, пока коллектор не готов принять значение (backpressure).

### 7.3. Оператор collect {#operator-collect}

`collect` — терминальный оператор: он запускает поток и начинает получать значения. `collect` — suspend-функция, поэтому вызывается из корутины. Поток выполняется, пока не завершится или пока корутина не будет отменена.

```kotlin
launch {
    countdown(5).collect { value ->
        println(value)
    }
    println("Готово")
}
```

Есть варианты: `collectLatest` (отменяет предыдущую обработку при новом значении), `single()` (завершается после первого значения, а при втором и последующих бросает `IllegalStateException`), `first()`, `toList()`. `collect` не возвращает значение — он запускает побочный эффект (обработку каждого элемента).

### 7.4. Flow vs suspend-функция {#flow-vs-suspend}

- Suspend-функция возвращает одно значение (или бросает исключение) и завершается. Подходит для разовых операций: «загрузить пользователя», «сохранить настройку».
- Flow возвращает потенциально много значений со временем. Подходит для наблюдения: «список сообщений», «состояние экрана», «таймер».

```kotlin
suspend fun getUser(id: Int): User        // одно значение
fun observeUser(id: Int): Flow<User>     // поток изменений
```

Flow можно рассматривать как suspend-функцию, которая может вызвать `emit` несколько раз. Если нужен только первый результат — используйте `first()` или обычную suspend-функцию; если нужна реактивность — Flow.

### 7.5. Холодный и горячий поток (обзорно) {#holodnyj-i-goryachij}

- Холодный поток (cold): код билдера запускается заново для каждого коллектора. Никаких значений не эмитится, пока кто-то не вызовет `collect`. Примеры: `flow { }`, `flowOf`, операторы. Каждый подписчик получает свою независимую последовательность.
- Горячий поток (hot): эмитит значения независимо от наличия коллекторов; новые подписчики получают только значения, эмитированные после подписки (или последнее закэшированное). Примеры: `StateFlow`, `SharedFlow`; `callbackFlow` сам по себе холодный и становится горячим только после `shareIn`/`stateIn`.

```kotlin
val cold = flow { emit(compute()) } // compute на каждый collect

val hot = MutableStateFlow(0) // хранит текущее значение
```

Холодные потоки экономят ресурсы (не работают без подписчиков), горячие — удобны для состояния, которое должно быть актуальным всегда. Подробнее — на следующем уровне (операторы `shareIn`, `stateIn`).

### 7.6. map и filter для Flow (базово) {#map-i-filter-flow}

Операторы Flow преобразуют поток и возвращают новый Flow. Они «ленивые»: не выполняются, пока не вызовут `collect`.

- `map { }` — преобразует каждое значение.
- `filter { }` — пропускает только значения, удовлетворяющие условию.

```kotlin
fun evenDoubled(flow: Flow<Int>): Flow<Int> =
    flow
        .filter { it % 2 == 0 }
        .map { it * 2 }
```

Операторы можно цепочкой. Каждый элемент проходит по всей цепочке. Важно: `map`/`filter` выполняются на диспетчере коллектора (по умолчанию). Переключение диспетчера для upstream делается через `flowOn` (следующий уровень).

### 7.7. StateFlow (вводное понятие) {#stateflow-vvodnoe}

`StateFlow` — горячий поток, хранящий одно текущее значение и отдающий его новым подписчикам сразу. Это реактивный контейнер состояния, замена `LiveData` в современных проектах. Всегда имеет начальное значение; повторные одинаковые значения не эмитятся (conflation по `equals`).

```kotlin
import kotlinx.coroutines.flow.MutableStateFlow
import kotlinx.coroutines.flow.StateFlow

class CounterViewModel {
    private val _count = MutableStateFlow(0)
    val count: StateFlow<Int> = _count

    fun increment() { _count.value += 1 }
}
```

Чтение: `count.value` (синхронно) или сбор через `collect`. Изменение только через `_count.value = ...` или `update { }`. `StateFlow` не завершается и не бросает исключений при сборе — он живёт, пока живёт область.

### 7.8. Сбор во ViewModel {#sbor-vo-viewmodel}

Во ViewModel корутины запускаются в `viewModelScope`, который отменяется при очистке ViewModel. Состояние экрана обычно хранят в `StateFlow` и собирают во View с учётом жизненного цикла.

```kotlin
class UserViewModel(
    private val repo: UserRepository
) : ViewModel() {

    val uiState: StateFlow<UiState> =
        repo.observeUser()
            .map { UiState.Success(it) }
            .stateIn(
                scope = viewModelScope,
                started = SharingStarted.WhileSubscribed(5000),
                initialValue = UiState.Loading
            )
}
```

Во View (Compose):

```kotlin
val state by viewModel.uiState.collectAsStateWithLifecycle()
```

Или во Fragment:

```kotlin
viewLifecycleOwner.lifecycleScope.launch {
    viewLifecycleOwner.repeatOnLifecycle(Lifecycle.State.STARTED) {
        viewModel.uiState.collect { render(it) }
    }
}
```

`repeatOnLifecycle` отменяет сбор при уходе экрана в фон и возобновляет при возврате — это предотвращает утечки и лишнюю работу. `collectAsStateWithLifecycle` делает то же для Compose.

**Мостик к следующему уровню (middle-coroutines):** дальше изучаются расширенные операторы (`flatMapLatest`, `combine`, `zip`, `debounce`, `distinctUntilChanged`), переключение диспетчера через `flowOn`, горячие потоки `SharedFlow` и `shareIn`/`stateIn` с разными стратегиями, обработка ошибок через `catch`, буферизация `buffer`/`conflate`, тестирование Flow через `Turbine` и виртуальное время. База, заложенная здесь (холодный поток, `emit`/`collect`, операторы, `StateFlow`, сбор во ViewModel), является фундаментом для всего этого.

**Типичные ошибки:**
- Сбор Flow напрямую в `lifecycleScope` без `repeatOnLifecycle` — лишняя работа в фоне и обновления UI, когда экран не виден.
- Использование `collect` в главном потоке для тяжёлых преобразований без `flowOn`.
- Создание `MutableStateFlow` с `null`-начальным значением без учёта UI-состояния.
- Сравнение StateFlow по ссылке вместо значения.
- Забытый `stateIn` — Flow остаётся холодным и перезапускается на каждую подписку.
