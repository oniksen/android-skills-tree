# android-skills-tree — agent guide

An Android developer skills tree / progress tracker. Users tick subtopics, earn XP and
crystals, keep a streak, unlock achievements. Data lives in Firebase Firestore; the UI is
server-rendered Next.js with client components talking to Firestore via hooks.

## Project map

- `src/app/` — App Router routes/layouts (thin): `page.tsx`, `layout.tsx`, `login/`, `(app)/`, `manifest.ts`, `globals.css`.
- `src/features/` — feature modules (`tree`, `roadmap`, `projects`, `shop`, `achievements`, `dashboard`, `profile`, `quiz`, `study`, `auth`) with `components/` and `actions/`.
- `src/shared/` — shared UI (`shared/ui`) and helpers (`shared/lib`).
- `src/core/` — domain (`core/domain`) and use-cases (`core/use-cases`).
- `src/ports/` — repository/service interfaces.
- `src/adapters/` — env, auth, firestore client commands/repositories.
- `src/composition/` — DI (`services-context.tsx`).
- `src/hooks/` — client Firestore hooks.
- `src/data/` — static content (skills, categories, levels, projects, shop, achievements).
- `content/` — study material Markdown sources (`content/study-materials/<grade>/<id>.md`).
- `scripts/` — build/release/materials/upload helper scripts.
- `src/lib/` — cross-cutting utils (`firebase`, `firestore`, `firestore-actions`, `version`, `viewport`, `theme`) + tests.
- `src/types/` — shared TypeScript types.
- Root: `next.config.ts`, `vitest.config.mts`, `eslint.config.mjs`, `tsconfig.json`.

## Stack & conventions

- Next.js 16 (App Router) + React 19, TypeScript. Firebase 12 (Firestore), Tailwind CSS v4,
  `motion` for animation, `lucide-react` icons. Tests with Vitest.
- Local Next.js docs: read `node_modules/next/dist/docs/` before using any Next API.
- Match existing patterns; keep domain logic in `src/lib`/`src/core` with a matching `*.test.ts`.

## Workflow rules

1. **Explore with Serena first.** Before reading many files, use Serena's semantic tools
   (`get_symbols_overview`, `find_symbol`, `find_referencing_symbols`) to pull only the
   symbols you need. Fall back to file reads only when Serena can't answer.
2. **Read memories at session start.** Serena keeps project knowledge in `.serena/memories/`
   (gitignored). Check it before re-deriving how the project works.
3. **Persist durable knowledge in the memory MCP.** Record cross-session facts and decisions
   (architecture choices, gotchas, "why") via the `memory` server so they survive new sessions.
4. **Plans and specs have a home.** Write task plans to `docs/superpowers/plans/YYYY-MM-DD-<topic>.md`
   and design docs to `docs/superpowers/specs/YYYY-MM-DD-<topic>.md`. Do not scatter plan files elsewhere.
5. **Verify before claiming done:** `npm run lint`, `npm run typecheck`, `npm test`.
6. **Commit subjects are user-facing release notes.** GitHub Releases are generated by
   semantic-release from conventional commits on push to `main`/`rc/*`. Write clear
   subjects (what changed for the user), use conventional types (`feat`, `fix`, `perf`, …),
   mark breaking changes explicitly. Do not create tags or release/version commits locally.
   Versioning details: "Release workflow (GitHub)".

## Release workflow (GitHub)

- `package.json` (`version`) — intended next stable base version; local UI shows `vX.Y.Z-dev+<sha>`.
- Local development: ordinary commits; no releases.
- Vercel deploys every branch as preview; GitHub releases are created only from `main` and `rc/*`.
- Release candidate: create branch `rc/X.Y.Z`, push it → Vercel preview deploy + GitHub pre-release `vX.Y.Z-rc.N`.
- Stable release: merge `rc/X.Y.Z` (or feature work) into `main` → GitHub release `vX.Y.Z`.
- UI shows only the base `vX.Y.Z` (pre-release/build suffix is hidden).
- Tags and releases are created by CI on push only; never create them locally.

## Automated feature cycle

- Start feature: `npm run new:feat -- <slug>` (minor bump) or `npm run new:fix -- <slug>` (patch bump).
- Develop locally; push the feature branch only if you need to save progress.
- Create release candidate: `npm run rc` (creates/pushes `rc/X.Y.Z`; CI creates `vX.Y.Z-rc.N`).
- Promote to stable: `npm run promote` (opens PR) or `npm run promote -- --merge` (merges; CI creates `vX.Y.Z`).

## Study material pipeline (Markdown → page)

Source of truth: `content/study-materials/<grade>/<id>.md`.
The generated registry `src/features/study/study-materials.generated.ts` is auto-built by
`scripts/generate-study-materials-registry.mjs` (`npm run generate:materials`; also runs in `prebuild`).
Never edit the generated file by hand.

### Required Markdown shape

```markdown
# <Название темы>

**Уровень:** Junior
**Категория:** <категория>
**Язык:** Kotlin
**Кратко:** <одно предложение для lead; optional>
**Футер:** <текст footer; optional>

## Содержание

1. [<Раздел>](#1-...)

---

# 1. <Раздел>

... H2/H3, code fences, study-* HTML blocks ...

# Итоговая самопроверка категории

...

## Источники и документация

### <Группа>
- [Title](https://...)
```

### Rendering contract (`StudyMarkdownRenderer` / `applyStudyPattern`)

- Requires **at least 2 H1**. If fewer, content is returned unchanged (legacy HTML materials).
- First H1 becomes `study-title`; metadata in the header area is parsed for hero/lead/footer.
- H1 sections after the first become `study-section` blocks with auto-generated `study-nav`.
- H2 → `study-subtitle`; H3 → `study-small`.
- H2 whose title contains `Источник` + following `- [Title](url)` lines → clickable `study-pill` links.
- Blank lines are required around raw HTML blocks; otherwise Markdown stops parsing.
- Inline code in headings must use backticks only; the renderer escapes `<`, `>`, `&`.

### Supported visual blocks

Use these exact class names and CSS variables only:
`study-hero`, `study-eyebrow`, `study-title`, `study-lead`, `study-nav`, `study-nav-link`,
`study-section`, `study-section-title`, `study-subtitle`, `study-grid`, `study-mini`,
`study-mini-title`, `study-note`, `study-note study-warn`, `study-table`, `study-flow`,
`study-node`, `study-arrow`, `study-pill`, `study-checklist`, `study-footer`, `study-muted`,
`study-small`, `study-tag`, `study-code`, `study-tree`, `study-diagram`.

### Authoring requirements

- Each study topic must cover **all** subtopics listed in `src/data/skills/<grade>.ts` for that skill.
- Target volume: **at least 700 words of clean information per topic** (excluding code blocks and HTML tags).
- Include concrete examples, real-world cases, and common mistakes/errors.
- Every topic page must have **anchor links (study-nav)** for each subtopic section.
- Keep `study-*` classes and structure; add new sections before the self-check section.

### Binding and routes

- Category: `studyMaterial: "<id>"` in `src/data/categories.ts`.
- Skill: `studyMaterial: "<id>"` in `src/data/skills/<grade>.ts`.
- Routes: `/tree/[slug]/category/[categoryId]/study` and `/tree/[slug]/skill/[skillId]/study`.
- Category/skill cards show `BookOpen` icon when `studyMaterial` is set.

### Commands

- Regenerate registry: `npm run generate:materials`
- Sync to Firestore: `npm run upload:study`
- Verify: `npm run lint`, `npm run typecheck`, `npm test`

### Gotchas

- `categoryId` in the registry mirrors the material `id`; it is not used for binding.
- Study checkboxes are visual-only; there is no persistence.
- Legacy HTML materials bypass `applyStudyPattern`.
- Do not commit generated changes unless they came from `npm run generate:materials`.
- `npm run prebuild` regenerates the registry before `npm run build`.

## Firestore listeners and quota

- One listener per user per domain: use a shared listener cache instead of creating `onSnapshot` in every component.
- Prefer `getDoc` + React Query with `staleTime`/`gcTime` for data where real-time is not critical.
- Always unsubscribe from listeners on unmount; never create listeners in loops or on every render.
- Run auto-sync (auto-freeze, backfill, checkAchievements) once per session (sessionStorage flag).
- Handle `resource-exhausted`: show a toast, avoid console spam, use exponential backoff.
- Cache static data (study materials, etc.) for 24h and disable `refetchOnWindowFocus`.
- Before adding a new listener, check if the read can be merged with an existing one.
