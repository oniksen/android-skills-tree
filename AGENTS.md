# android-skills-tree — agent guide

An Android developer skills tree / progress tracker. Users tick subtopics, earn XP and
crystals, keep a streak, unlock achievements. Data lives in Firebase Firestore; the UI is
server-rendered Next.js with client components talking to Firestore via hooks.

## Project map

- `src/app/` — App Router routes/layouts (thin): `page.tsx`, `layout.tsx`, `login/`, `(app)/`, `manifest.ts`, `globals.css`.
- `src/features/` — feature modules (`tree`, `roadmap`, `projects`, `shop`, `achievements`, `dashboard`, `profile`, `quiz`, `study`, `auth`) with `components/` and `actions/`.
- `src/shared/` — shared UI (`shared/ui`) and helpers (`shared/lib`).
- `src/core/` — domain (`core/domain`) and use-cases (`core/use-cases`).
- `src/ports/` — repository/service interfaces.
- `src/adapters/` — env, auth, firestore client commands/repositories.
- `src/composition/` — DI (`services-context.tsx`).
- `src/hooks/` — client Firestore hooks.
- `src/data/` — static content (skills, categories, levels, projects, shop, achievements).
- `src/lib/` — cross-cutting utils (`firebase`, `firestore`, `firestore-actions`, `version`, `viewport`, `theme`) + tests.
- `src/types/` — shared TypeScript types.
- Root: `next.config.ts`, `vitest.config.mts`, `eslint.config.mjs`, `tsconfig.json`.

## Stack & conventions

- Next.js 16 (App Router) + React 19, TypeScript. Firebase 12 (Firestore), Tailwind CSS v4,
  `motion` for animation, `lucide-react` icons. Tests with Vitest.
- Local Next.js docs: read `node_modules/next/dist/docs/` before using any Next API.
- Match existing patterns; keep domain logic in `src/lib`/`src/core` with a matching `*.test.ts`.

## Workflow rules

1. **Explore with Serena first.** Before reading many files, use Serena's semantic tools
   (`get_symbols_overview`, `find_symbol`, `find_referencing_symbols`) to pull only the
   symbols you need. Fall back to file reads only when Serena can't answer.
2. **Read memories at session start.** Serena keeps project knowledge in `.serena/memories/`
   (gitignored). Check it before re-deriving how the project works.
3. **Persist durable knowledge in the memory MCP.** Record cross-session facts and decisions
   (architecture choices, gotchas, "why") via the `memory` server so they survive new sessions.
4. **Plans and specs have a home.** Write task plans to `docs/superpowers/plans/YYYY-MM-DD-<topic>.md`
   and design docs to `docs/superpowers/specs/YYYY-MM-DD-<topic>.md`. Do not scatter plan files elsewhere.
5. **Verify before claiming done:** `npm run lint`, `npm run typecheck`, `npm test`.
6. **Commit subjects are user-facing release notes.** GitHub Releases are generated by
   semantic-release from conventional commits on push to `main`/`rc/*`. Write clear
   subjects (what changed for the user), use conventional types (`feat`, `fix`, `perf`, …),
   mark breaking changes explicitly. Do not create tags or release/version commits locally.
   Versioning details: "Release workflow (GitHub)".

## Release workflow (GitHub)

- `package.json` (`version`) — intended next stable base version; local UI shows `vX.Y.Z-dev+<sha>`.
- Local development: ordinary commits; no releases.
- Vercel deploys every branch as preview; GitHub releases are created only from `main` and `rc/*`.
- Release candidate: create branch `rc/X.Y.Z`, push it → Vercel preview deploy + GitHub pre-release `vX.Y.Z-rc.N`.
- Stable release: merge `rc/X.Y.Z` (or feature work) into `main` → GitHub release `vX.Y.Z`.
- UI shows only the base `vX.Y.Z` (pre-release/build suffix is hidden).
- Tags and releases are created by CI on push only; never create them locally.

## Automated feature cycle

- Start feature: `npm run new:feat -- <slug>` (minor bump) or `npm run new:fix -- <slug>` (patch bump).
- Develop locally; push the feature branch only if you need to save progress.
- Create release candidate: `npm run rc` (creates/pushes `rc/X.Y.Z`; CI creates `vX.Y.Z-rc.N`).
- Promote to stable: `npm run promote` (opens PR) or `npm run promote -- --merge` (merges; CI creates `vX.Y.Z`).

## Study material authoring

- Each study topic must cover **all** subtopics listed in `src/data/skills.ts` for that skill.
- Target volume: **at least 700 words of clean information per topic** (excluding code blocks and HTML tags). If a topic requires more to be fully covered at Junior level, exceed this — completeness takes priority over the number.
- Include concrete examples, real-world cases, and common mistakes/errors for each concept.
- Every topic page must have **anchor links (study-nav) for each subtopic section** so users can jump quickly.
- Keep the existing `study-*` CSS classes and structure; add new sections before the self-check section.
- After editing materials, run `npm run lint`, `npm run typecheck`, `npm test`, then `node scripts/upload-study-materials.mjs` to sync to Firebase.
