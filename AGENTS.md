# android-skills-tree — agent guide

An Android developer skills tree / progress tracker. Users tick subtopics, earn XP and
crystals, keep a streak, unlock achievements. Data lives in Firebase Firestore; the UI is
server-rendered Next.js with client components talking to Firestore via hooks.

## Project map

- `src/app/` — App Router routes/layouts (thin): `page.tsx`, `layout.tsx`, `login/`, `(app)/`, `manifest.ts`, `globals.css`.
- `src/features/` — feature modules (`tree`, `roadmap`, `projects`, `shop`, `achievements`, `dashboard`, `profile`, `quiz`, `study`, `auth`) with `components/`, `model/` and `actions/`.
- `src/shared/` — shared UI (`shared/ui`) and helpers (`shared/lib`).
- `src/core/` — domain (`core/domain`) and use-cases (`core/use-cases`).
- `src/ports/` — repository/service interfaces.
- `src/adapters/` — env, auth, firestore client commands/repositories.
- `src/composition/` — DI (`services-context.tsx`).
- `src/hooks/` — client Firestore hooks.
- `src/data/` — static content (skills, categories, levels, projects, shop, achievements).
- `content/` — study material Markdown sources (`content/study-materials/<grade>/<id>.md`).
- `scripts/` — build/release/materials/upload helper scripts.
- `src/lib/` — cross-cutting utils (`firebase`, `firestore`, `firestore-actions`, `version`, `viewport`, `theme`) + tests.
- `src/types/` — shared TypeScript types.
- Root: `next.config.ts`, `vitest.config.mts`, `eslint.config.mjs`, `tsconfig.json`.

## Stack & conventions

- Next.js 16 (App Router) + React 19, TypeScript. Firebase 12 (Firestore), Tailwind CSS v4,
  `motion` for animation, `lucide-react` icons. Tests with Vitest.
- Local Next.js docs: read `node_modules/next/dist/docs/` before using any Next API.
- Match existing patterns; keep domain logic in `src/lib`/`src/core` with a matching `*.test.ts`.

## Workflow rules

1. **Explore with Serena first.** Before reading many files, use Serena's semantic tools
   (`get_symbols_overview`, `find_symbol`, `find_referencing_symbols`) to pull only the
   symbols you need. Fall back to file reads only when Serena can't answer.
2. **Read memories at session start.** Serena keeps project knowledge in `.serena/memories/`
   (gitignored). Check it before re-deriving how the project works.
3. **Persist durable knowledge in the memory MCP.** Record cross-session facts and decisions
   (architecture choices, gotchas, "why") via the `memory` server so they survive new sessions.
4. **Plans and specs have a home.** Write task plans to `docs/superpowers/plans/YYYY-MM-DD-<topic>.md`
   and design docs to `docs/superpowers/specs/YYYY-MM-DD-<topic>.md`. Do not scatter plan files elsewhere.
5. **Verify before claiming done:** `npm run lint`, `npm run typecheck`, `npm test`.
   Node: Vercel builds on 24.x; `npm test` needs Node `^22.22` or `>=24.8` (html-validate 11);
   `next build`, `lint`, `typecheck` work from Node 20.9.
6. **Commit subjects are user-facing release notes.** GitHub Releases are generated by
   semantic-release from conventional commits on push to `main`/`rc/*`. Write clear
   subjects (what changed for the user), use conventional types (`feat`, `fix`, `perf`, …),
   mark breaking changes explicitly. Do not create tags or release/version commits locally.
   Versioning details: "Release workflow (GitHub)".

## Release workflow (GitHub)

- **Semantic-release is the single source of truth for versions.** On push to `main`/`rc/*`
  it reads the last stable git tag and the conventional commits since it
  (breaking → major, `feat` → minor, `fix`/`perf` → patch).
- `package.json` (`version`) is only the local/dev base shown by the UI as `vX.Y.Z-dev+<sha>`.
  The release step never reads it. Keep it at the latest released tag; do not bump it by hand.
- Local development: ordinary commits; no releases.
- Vercel deploys every branch as preview; GitHub releases are created only from `main` and `rc/*`.
- Release candidate: `npm run rc` creates `rc/<next version>` (the next version comes from the
  last tag + commits, see `scripts/release-version.mjs`). Push it → GitHub pre-release
  `vX.Y.Z-rc.N`.
- Stable release: merge `rc/X.Y.Z` (or feature work) into `main` → GitHub release `vX.Y.Z`.
- UI shows only the base `vX.Y.Z` (pre-release/build suffix is hidden).
- Tags and releases are created by CI on push only; never create them locally.

## Automated feature cycle

- Start feature: `npm run new:feat -- <slug>` or `npm run new:fix -- <slug>` — creates the
  branch from `main` (or `--base=<branch>`) without touching versions or `package.json`.
- Develop locally; push the feature branch only if you need to save progress.
- Create release candidate: `npm run rc` (creates/pushes `rc/<next>`; CI creates
  `v<next>-rc.N`).
- Promote to stable: `npm run promote` (uses the current `rc/*` branch, or the newest one;
  opens a PR) or `npm run promote -- --merge` (merges; CI creates the stable release).

## Study material pipeline (Markdown → page)

Source of truth: `content/study-materials/<grade>/<id>.md`.
Authoring rules live in `STUDY_MATERIALS_FORMATTING.txt` at the repo root — read it before
adding or editing a material. Files are plain GFM: raw HTML is not supported.

The generated registry `src/features/study/study-materials.generated.ts` is auto-built by
`scripts/generate-study-materials-registry.mjs` (`npm run generate:materials`; also runs in `prebuild`).
Never edit the generated file by hand.

### Rendering

- `src/features/study/model/parse-study-document.ts` → `parseStudyDocument()` returns
  `{ meta, sections }`; H1 is the page title, H2 are sections (legacy multi-H1 files are
  still accepted), `## Содержание` is dropped, sources sections are flagged.
- `src/features/study/model/study-blocks.ts` → `STUDY_BLOCK` / `STUDY_BLOCK_MAP`: the only
  place where `study-*` class names are declared. Components resolve every class through
  `blockClass("note")` — no component imports `STUDY_BLOCK` directly and no `study-*` string
  is written by hand. Each registry entry lists the HTML `tags` it is really rendered as and
  a `layout`; `study-blocks.test.ts` fails if the registry and `globals.css` drift apart or
  if a component goes back to reading classes straight from `STUDY_BLOCK`.
- `src/features/study/components/study-block-renderer.tsx` → `STUDY_BLOCK_RENDERERS`: the one
  map from `StudySectionBlock["type"]` to a React component, typed with
  `satisfies Record<…>` so a missing entry is a compile error. `StudySection` has no
  `if (block.type === …)` branching left.
- `src/features/study/model/markdown-pipeline.ts` is the single Markdown processor of the
  client bundle: one `unified()` built at module import, a FIFO tree cache and
  `renderMarkdown()`. `StudyProse`/`StudyInline` must not use `<ReactMarkdown>` — a guard test
  fails if they do; `components/__fixtures__/study-render/*.html` is a byte-exact golden
  baseline that is never regenerated to make a test pass. Regenerate it only deliberately:
  `npm run study:golden`, then review the diff; a diff in a material baseline without a
  content edit is a regression.
- `src/features/study/components/markdown-components.tsx` maps Markdown tags to blocks:
  tables get a scroll wrapper, fences become `StudyCodeBlock`, task lists become
  checklists, link lists in sources sections become pills, a standalone image becomes a
  `figure` instead of a `figure` wrapped in `p`.
- `:::cards` is the only directive: `- **Заголовок** — текст` items become a responsive grid.
  `parseStudySectionBody` is the only place that recognises it; a `:::` inside a fenced code
  block does not close the directive, and an unclosed `:::cards` keeps its body as Markdown
  (the opener is dropped, so the raw marker never reaches the page).
- Blockquotes become notes; `> [!WARNING]` / `> [!CAUTION]` switch the warning variant, and a
  new marker after a blank line starts a new note instead of merging into the previous one.
- Phones keep the same blocks edge to edge (no side borders, inner padding preserved);
  code, tables and card grids scroll inside their own container.

### Adding or changing a block

1. Extend `StudySectionBlock` in `parse-study-document.ts` and parse it there.
2. Add the class(es) to `STUDY_BLOCK`/`STUDY_BLOCK_MAP` in `study-blocks.ts` and style them
   in `globals.css`.
3. Add the renderer to `STUDY_BLOCK_RENDERERS` and cover it in `study-block-renderer.test.tsx`.
4. If it changes the emitted markup, add it to the fixture in `study-html-validity.test.tsx`;
   that test validates every material with `html-validate:recommended`.

### Binding and routes

- Category: `studyMaterial: "<id>"` in `src/data/categories.ts`.
- Skill: `studyMaterial: "<id>"` in `src/data/skills/<grade>.ts`.
- Routes: `/tree/[slug]/category/[categoryId]/study` and `/tree/[slug]/skill/[skillId]/study`.
- Cards show a `BookOpen` icon when `studyMaterial` is set.

### Commands and gotchas

- Regenerate registry: `npm run generate:materials`
- Sync to Firestore: `npm run upload:study`
- Verify: `npm run lint`, `npm run typecheck`, `npm test`
- `categoryId` in the registry mirrors the material `id`; it is not used for binding.
- Study checkboxes are visual-only; there is no persistence.
- Study text is looked up on the server (`fetchStudyMaterial`); never import
  `study-material.ts` / `study-materials.generated.ts` from a client component.
- Do not commit generated changes unless they came from `npm run generate:materials`.

## Roadmap dependency graph and diagram

The `/roadmap` page is designed to show **all** skills of the current grade as a graph on
`xl+` while keeping the existing flat `GapList` below `xl`. Implementation plan:
`docs/superpowers/plans/2026-11-23-roadmap-dependency-diagram.md`.

- **Edges (source of truth):** `src/data/roadmap-links.ts` exports `ROADMAP_LINKS`
  (`{ from, to, kind: "requires" | "recommends" }`) keyed by existing skill IDs.
  `requires` draws a solid arrow, `recommends` a dashed one. Edges are same-grade only;
  the data test rejects cross-grade edges. Add links only in this file; do not add
  prerequisite fields to `src/data/skills/*`.
- **Domain:** `src/core/domain/roadmap-graph.ts` → `buildRoadmapGraph({ levelId,
  assessmentMap, links })`. It includes every skill of the grade, groups them into
  category columns ordered by `sortOrder` (`column`, `row`), and assigns `done` (100%),
  `in-progress` (partial) or `remaining` (0%) plus the `requiredForLevelUp` flag.
  Edges with unknown or cross-grade endpoints are dropped at runtime; the data test must
  reject them. There is no ancestor filtering and no topological layer pass.
- **Renderer:** `src/features/roadmap/components/RoadmapDiagram.tsx` renders category
  columns as hand-rolled SVG (no graph library, no pan/zoom; horizontal scroll). Nodes
  are `<g role="link">` and use `treeSkillHref` / `skillDetailHref`; status colors are
  emerald / blue / slate. A non-required skill (`requiredForLevelUp === false`) gets a
  dashed stroke; required skills are solid. Empty graphs render a message, not an empty
  `<svg>`.
- **Responsive:** `RoadmapClient` renders the diagram in `hidden xl:block` and the
  `GapList` in `xl:hidden`; the sort toolbar is `xl:hidden` because it only sorts the
  list. The skeleton is unchanged.
- **Invariants/tests:** every `from`/`to` must exist in `skills`, edges must be unique,
  same-grade and acyclic (`src/data/roadmap-links.test.ts`); graph behavior is covered by
  `src/core/domain/roadmap-graph.test.ts`; the diagram by `RoadmapDiagram.test.tsx`.
  Never add a graph library for this feature.
- **Verify:** `npm run lint`, `npm run typecheck`, `npm test`.

## Firestore data model and listeners

- Source of truth: single state document `users/{uid}/state/current` (`UserState`).
  Old collections `progress/current`, `assessments`, `projects`, `achievements`,
  `currency/current`, `streaks/current`, `settings/current` are legacy
  migration/rollback data only and are no longer written by the app.
- One state listener per user: `useUserState` + `userStateStore` (live-store keyed
  by `uid`), not six domain listeners. The listener outlives the page and is
  cleared only on user change (`session-reset.ts`).
- Lazy migration on first read: `readLegacyUserState` (in
  `src/adapters/firestore-client/state.ts`) is the only legacy reader; it runs
  once when `state/current` is missing and stamps `migratedAt`.
- Pages paint from the cached snapshot (`useLiveStore` + `useSyncExternalStore`);
  a full-screen skeleton is only acceptable while the first snapshot is in flight.
- Prefer `getDoc` + React Query with `staleTime`/`gcTime` for data where
  real-time is not critical. Never create listeners in loops or on every render;
  use the shared `useFirebaseAuth` state.
- Run auto-sync (auto-freeze, backfill, checkAchievements) once per session
  (`oncePerSession`).
- Handle `resource-exhausted`: show a toast, avoid console spam, use exponential
  backoff.
- Cache static data (study materials, etc.) for 24h and disable
  `refetchOnWindowFocus`.
- Before adding a new listener, check if the read can be merged with the existing
  state listener.
- Firestore uses persistent IndexedDB cache with multi-tab support
  (`persistentLocalCache` + `persistentMultipleTabManager`).
- App Check is optional and activates only when
  `NEXT_PUBLIC_RECAPTCHA_SITE_KEY` is set; enforce App Check in the Firebase
  console before relying on it.
- User-visible timestamps are written with `serverTimestamp()`; never put the
  returned `FieldValue` into the optimistic live-store cache. `normalizeUserState`
  converts Firestore timestamps back to `Date` on read.
- `reconcileAchievements` is transactional; `checkAchievements`, `syncStreak` and
  `applyAutoFreezes` are serialized per uid via `src/shared/lib/user-state-lock.ts`.
- Dev-only read/write counters are exposed as `window.__firestoreMetrics`
  (`src/shared/lib/firestore-metrics.ts`).

## Routing, auth and caching

- Protected routes are enforced in `src/proxy.ts` (`protectedRoutes`), not in page components. Pages stay static (○) / SSG (●) so `<Link>` can prefetch the whole page; do not add `cookies()`/`headers()` to a page under `(app)`.
- Adding a new protected page: add its path to `protectedRoutes` in `src/proxy.ts`.
- `experimental.staleTimes` (30s dynamic / 300s static) keeps the client router cache warm for dynamic `/tree/**` routes.
- Server components under `(app)` must not await slow network calls: the layout version lookup is bounded by `AbortSignal.timeout(2s)` and memoized.
- Study material text is looked up on the server (`fetchStudyMaterial`); never import `study-material.ts` / `study-materials.generated.ts` from a client component — it pulls ~1 MB into the bundle.
